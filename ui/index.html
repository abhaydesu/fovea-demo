The problem

Flow tools tell you a call failed. They can't tell you why.

Tracing frameworks need code in every service. eBPF tools like Cilium and Hubble need none, but they only see network metadata: who talked to whom, ports, bytes. The message that explains the failure is invisible.

Flow metadatawhat a flow view shows (illustrative)
orders:41488  →  inventory:8082
TCP   ESTABLISHED   FORWARDED
5 packets · 812 bytes · 0.4 ms

You know which hop broke. You don't know what it said.

Foveawhat Fovea reconstructs from the same connection
POST /reserve  {"item":"widget","qty":50}
← 500  {"error":"insufficient stock",
         "available":3, "requested":50}

The root cause, in the payload, at the hop where it originated.

How it works

Four stages. Zero code changes.

01

Capture

eBPF tracepoints on read, write, sendmsg and friends copy socket bytes at the syscall boundary. Filtered in-kernel to the workloads' cgroups.

02

Reassemble

A Go agent stitches chunks into complete HTTP/1.1 messages, pairs each request with its response and merges the client and server views into one call.

03

Correlate

Processes and IPs resolve to service names. Payloads join their network flow by 4-tuple, and calls chain into a request path with the root cause flagged.

04

Explore

A web UI shows the live service map, every network flow and the exact messages exchanged, with credentials and PII redacted.

    Flow counterA TC program counts packets and bytes per connection. This is the Hubble-style metadata.
  4. 4
    cgroup filterOnly the watched workloads pass. Every other process is dropped inside the kernel.
  5. 5
    Ring bufferThe kernel-to-agent queue. If it overflows, events are counted as dropped, never silently lost.
  6. 6
    ReassemblerThe Go agent stitches chunks into whole HTTP calls and merges both ends of each one.
  7. 7
    CorrelatorCalls are linked into a chain. The deepest failing hop becomes the root cause.
